RecoverSense

An adaptive recovery decision engine for Indian recurring payments — it diagnoses why a payment failed, chooses a recovery strategy under merchant-defined policy, executes it, and verifies the money actually came back.

RecoverSense gives revenue recovery a sixth sense — it understands what went wrong before deciding what to do next.

01

The problem

Revenue doesn't leak in one clean step. A card declines, a UPI Autopay mandate lapses, an eNACH debit bounces, a subscription silently goes dormant. Most systems answer this with one move: retry, on a timer, regardless of why it failed.

A blind retry on insufficient_funds is reasonable. The same blind retry on mandate_revoked is wasted — the underlying authorization no longer exists, so nothing will succeed until the customer re-authorizes. Every payment platform we examined optimizes when to retry. Almost none of them make an explicit, auditable decision about what kind of recovery action a specific failure actually needs.

For Indian recurring payments specifically, this gap is sharper: UPI Autopay and eNACH mandates can be revoked, expired, or cancelled outright — a state retry logic can't fix, and re-acquiring a mandate is a materially different workflow (fresh AFA authentication) from re-charging a card.

03

Thesis

The honest, defensible version of the pitch — no overclaiming.

Positioning statement. Existing recovery systems optimize individual mechanisms — retry timing, dunning emails, card-update prompts. RecoverSense prototypes an explicit decision layer that evaluates the failure state and selects among multiple recovery actions under merchant-defined financial policy, then proves — not just claims — that the recovery worked.

Three things carry the differentiation: diagnosis before action (classify the failure, don't assume it), policy before execution (an LLM proposes, a deterministic engine approves), and verification before counting it as recovered (check the business state changed, not just that an API call returned 200).

04

Architecture

Six stages. The LLM only occupies one of them — diagnosis. Everything that touches money is deterministic and logged.

01
Diagnosis
LLM classifies the failure from Razorpay's source / step / reason payload + payment history into one of five failure types, with a confidence score.
02
Strategy
Deterministic router maps diagnosis → one of five recovery strategies. No LLM in this step — same failure type, same strategy, every time.
03
Policy gate
Checks the proposed action against retry limits, amount limits, subscription state, and duplicate-action protection before anything executes.
04
Execution
Calls the real Razorpay test API where an endpoint exists; falls back to a clearly-labelled deterministic simulator where it doesn't (e.g. arbitrary mandate-state injection).
05
Verification
Re-fetches state after execution and diffs expected vs. actual — the same pattern used to verify test outcomes in QA automation, applied to money movement.
06
Audit
Every decision, check, and outcome above is written to an immutable, timestamped log — the artifact judges actually look at.
Why the LLM is boxed in. An LLM proposing REACQUIRE_MANDATE is a suggestion, not an instruction. Nothing that moves money or changes subscription state executes without passing the deterministic policy engine first. This is the guardrail a judge will ask about — have the answer ready before they ask.
05

Decision logic

The failure-type → strategy mapping, locked before any code is written.

Failure diagnosisSignalStrategy
Insufficient funds 1st–2nd attempt WAIT_AND_RETRY
Insufficient funds 3rd+ attempt PAYMENT_LINK
Payment-method issue (expired card, bad CVV) any attempt PAYMENT_LINK
Temporary / technical failure timeout, gateway error WAIT_AND_RETRY (extended backoff)
Mandate issue (revoked, expired, cancelled) active subscription RE_ACQUIRE_MANDATE
Repeated failure (3+ in 24h) or high amount any type ESCALATE
Subscription already cancelled any type STOP — no attempt made

The "avoided unnecessary attempts" metric (§08) comes directly from this table: every row that resolves to STOP or routes straight to ESCALATE instead of retrying is a wasted attempt the system chose not to make.

06

Policy engine

The LLM proposes an action; this is what has to approve it before anything executes.

// proposed action, from the diagnosis + strategy stages
{
  "action": "REACQUIRE_MANDATE",
  "subscription_id": "sub_8f21c",
  "amount": 2499,
  "reason": "mandate_revoked",
  "confidence": 0.94
}

// policy engine — deterministic, no LLM in this path
checks = {
  retry_limit_not_exceeded:        retry_count < 3,
  subscription_state_valid:        subscription.status == "active",
  customer_active:                 customer.is_active,
  no_pending_reacquisition:        !has_pending_reacquisition(sub_id),
  amount_within_policy:            amount <= 50000,
  // money-movement actions only — guards against acting on stale state
  not_already_settled_elsewhere:   !payment_settled_via_other_channel(sub_id),
  webhook_delay_window_respected:  time_since_last_webhook >= min_wait_window
}

// all must pass — any single failure blocks execution and logs why
approved = all(checks.values())

Seven checks for the MVP. The first five gate which action is allowed: retry-count limit, amount ceiling, subscription-state validity, customer-active status, and duplicate-action protection (never trigger two mandate re-acquisitions on the same subscription at once). The last two exist specifically for actions that move money: don't retry or re-acquire if the payment already settled through another channel the agent hasn't seen yet, and don't act inside the window where a delayed webhook could still arrive and change the picture. Every check — passed or failed — is written to the audit log, not just the final verdict.

Why this matters beyond the checklist. An LLM recommending an action off a snapshot of state is inherently working with slightly stale information — a customer could have paid via a different link, a webhook could be seconds from landing. The last two checks exist to stop the system from acting confidently on information that's already out of date. This is the difference between an agent that recommends and a system that's safe to let recommend things that move money.
Scope lock — Aug 26. The architecture and positioning in this document are final for the Sep 2 submission. The framing is deliberately PSP-agnostic — the policy and verification layer is architected behind a service interface, with Razorpay as the reference implementation, not a Razorpay-only feature — but no second payment gateway gets built or integrated before the deadline; that claim is proven by the architecture, not by a second integration. Re-litigating "is this differentiated enough" from here forward costs a day of thinking for zero days of building, and the deadline doesn't move. Next open question gets a one-line answer and a return to code, not a new research pass.
07

Verification

The part that turns "we called an API" into "we confirmed it worked" — inherited directly from prior QA automation work.

Every execution follows the same four-step check used in test automation: define the expected state, capture the actual state, diff them, record pass or fail. Applied here:

  • Action — the approved action was executed against the Razorpay test API (or simulator)
  • Expected state — what should be true afterward (e.g. new subscription exists, status authenticated, correct customer, correct amount)
  • Actual state — re-fetched via GET /v1/subscriptions/{id} after execution, not assumed from the write response
  • Result — VERIFIED or FAILED, logged with the specific field that didn't match on failure
Why this matters more than it sounds like it should. A recovery system that logs "action executed" without checking the resulting state can silently over-report recovery. Verifying the actual subscription/mandate/payment state after every action is what makes the recovery-rate metric trustworthy rather than aspirational.
08

Metrics

What gets reported at the end — computed from the audit log, not asserted separately.

Revenue at risk
Total ₹ across all failed payments entering the system in the test run.
Recovered revenue
₹ where the post-action state was independently verified, not just attempted.
Recovery rate
Recovered ÷ at-risk, and separately, per strategy (retry / link / re-acquire).
Diagnosis accuracy
Predicted failure type vs. ground-truth label on synthetic test data.
Strategy accuracy
Predicted strategy vs. ground-truth optimal strategy for that failure.
Avoided unnecessary attempts
Cases routed to STOP or ESCALATE instead of a wasted retry.
Policy violations blocked
Proposed actions the policy engine rejected before execution, and why.
Verification success rate
Share of executed actions whose resulting state matched expectation.
09

Scope

What ships for Sep 2, and what's explicitly left out — stated up front so nothing gets discovered under deadline pressure.

In scope
  • 5 failure types, 5 recovery strategies, 2 terminal states (escalate, stop)
  • Diagnosis via LLM against real Razorpay test-mode error payloads
  • Deterministic policy engine — 7 checks
  • Execution via real Razorpay test API (payment links, subscription create/cancel) wherever an endpoint exists
  • Simulator, clearly labelled, only where test infra has no endpoint (arbitrary mandate-state injection)
  • Post-action verification against re-fetched state
  • Full audit trail, exportable
  • Metrics report computed from the audit log
Out of scope
  • Production UPI/eNACH integration — AFA authentication is simulated, not real
  • WhatsApp / voice recovery channels
  • Custom ML model — diagnosis uses the Claude API, not a trained classifier
  • Multi-agent orchestration — one agent, five tools, one policy engine
  • Causal/counterfactual uplift measurement — any control-group comparison is labelled synthetic, not real merchant data
  • More than 3 recovery strategies in the working demo path

Backend shape

com.recoversense
├── controller     PaymentController · RecoveryController · DashboardController · AuditController
├── service        DiagnosisService · StrategyService · PolicyService
│                   RecoveryService · VerificationService · AuditService
├── integration     RazorpayClient · ClaudeClient · MandateSimulator
├── model          Payment · RecoveryCase · RecoveryDecision · RecoveryAction · AuditEvent
└── repository

One Spring Boot application. RazorpayClient is the single place HTTP calls to Razorpay happen — nothing scattered across services. RecoveryService orchestrates diagnosis → strategy → policy → execution → verification → audit in that fixed order, synchronously; the dataset is demo-scale, not production traffic, so blocking calls are the right call, not WebClient/reactive.

Using
  • Docker Compose — Postgres + backend + frontend, for a reproducible demo (skip if it eats a day; local run for the recording is fine)
  • Springdoc OpenAPI / Swagger — free documentation, reinforces the API/QA story
Deliberately not using
  • LangChain / LangGraph — the workflow is deterministic; plain services are clearer
  • n8n — reads as an automation prototype, not an engineered system
  • Kafka, Redis, Kubernetes — no queue, cache, or orchestration problem exists at this scale
  • Microservices — one Spring Boot app end to end
  • Vector DB / RAG — payment context is structured data, not a retrieval problem
If Aug 30 arrives and the core isn't done yet, cut in this order: Playwright E2E first (tell the QA story from JUnit + Postman instead), then Swagger, then Docker Compose, then chart polish. Never cut the policy engine, verification engine, audit service, or structured-JSON diagnosis — those four are what the whole pitch rests on.
